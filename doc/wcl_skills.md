## 1. LLM → Context → Tool → Agent → Harness → MCP

1.1 首先是 **LLM**，也就是大语言模型，负责理解和生成。

1.2 在 LLM 之上是 **Context**，也就是上下文。Agent 并不是简单地把用户的一句话直接丢给模型，而是要把系统提示、历史对话、工具信息、任务状态等内容组织成模型能够理解的 Context，这里面涉及到 Context Engineering（上下文工程）。

1.3 然后是 **Tool**。当模型本身无法完成某件事情时，可以通过 Tool Calling 调用外部能力，比如执行代码、读写文件、搜索、调用 API 等。

1.4 再往上就是 **Agent**。Agent 本质上是一个循环（Agent Loop）：让模型判断下一步做什么，需要调用工具就调用工具，拿到工具结果以后继续推理，直到任务完成。

1.5 **Harness** 我理解成 Agent 的运行时。它负责把 LLM、Context、Tool、Session、State、Event、权限、错误处理等这些东西真正组织起来，让 Agent 能够持续运行，而不是单纯调用一次模型 API。

1.6 最后是 **MCP**。MCP 更偏向于解决 Agent 与外部工具和数据之间的标准化连接问题，让 Tool、Resource 等能力可以通过统一协议接入 Agent。

1.7 所以我现在理解这条链路，实际上就是：
**LLM 是模型能力，Context 是模型看到的信息，Tool 是模型可以调用的外部能力，Agent 是基于模型和工具进行自主循环的逻辑，Harness 是承载 Agent 的运行底座、驾驶舱，MCP 则是连接外部工具和数据的一种标准协议。**

## 2. 使用AI解决ANR

当时我们线上有大量 ANR，但是一个比较大的难点是，很多问题属于线上低概率场景，本地很难稳定复现。如果完全按照传统方式，一个 ANR 一个 ANR 地人工分析，效率比较低，而且很难把同一类问题一次性解决。
所以我当时换了一个思路：**让 AI 先从线上 ANR 中总结问题模式，再反过来扫描整个代码仓库，寻找同类风险。**

第一步，我让 AI 对线上 ANR 进行分类和归纳。
比如比较典型的有：**主线程阻塞 I/O、锁竞争和死锁、同步 Binder 调用耗时、主线程耗时计算、线程池阻塞或耗尽，以及 Broadcast、Service 等组件执行超时。**

第二步，不只是让 AI 告诉我“这个 ANR 是什么原因”，而是让 AI 针对每一类问题提取**代码特征**。
比如锁竞争，就去关注 `synchronized`、`Lock` 等同步代码；阻塞等待，就关注 `Future.get()`、`CountDownLatch.await()` 等可能产生长时间等待的代码；主线程 I/O，就重点寻找数据库、文件等阻塞操作；Binder 问题，则重点关注主线程上的同步 Binder 调用。然后我让 AI 去扫描本地代码仓库，根据这些特征和上下文，寻找可能存在同类问题的代码。

第三步，就是让 AI 对这些高风险代码进行分析和修复。
因为很多线上 ANR 根本无法在本地复现，所以这里采用的不是传统的“复现问题再修复”，而是**根据线上 ANR 的特征，总结出问题模式，再反向扫描代码进行风险治理**。

整个过程大概就是：
**线上 ANR → AI 分析归类 → 提取问题模式 → 提取代码特征 → AI 扫描代码仓库 → 定位高风险代码 → AI 辅助修复 → 线上指标验证。**
经过几轮这样的治理之后，线上整体 ANR 率从大约 **7% 降到了 3%**。
这个项目让我比较明确地认识到，AI 在工程问题上比较有价值的地方，不只是帮开发者写代码，而是可以把一个原本依赖人工经验的问题，抽象成**模式识别、代码检索、风险定位和批量治理**的流程。

## 3. AI代码友好仓库

我把一个比较老的 Android 代码仓库做了一次 AI 化改造。
核心目的很简单：**避免 AI 每次进入项目都要从头考古代码，浪费大量时间和 Token 建立 Context。**
我让 AI 先完整分析整个项目的模块、依赖关系、核心业务和关键类，然后建立一套分层的项目知识文档：从根目录的项目总览，到各个模块、功能和核心类的说明，并通过链接形成完整的导航关系。
这样以后 AI 进入项目，可以先通过这套知识地图快速定位到相关模块和代码，而不是从源码开始一点一点摸索。
**本质上，就是通过改造代码仓库，为 AI 提供更好的 Context，让 AI 更快理解项目、更快定位问题、更少消耗 Token。**
最终的目标就是让 AI 从“进入一个陌生老项目，需要重新考古”，变成“进入项目以后，有一套完整的知识地图可以沿着导航快速建立 Context”。

## 4. AI编程的精髓是双向同步

**第四个是我对 AI 编程的一种实践：我认为 AI 编程的精髓之一是代码和文档的双向同步。**
比如我之前做过一个比较复杂的投放数据归因模块，里面有多种规则、事件匹配、优先级和接口调用关系。
我会在这个代码模块下面建立一份 Markdown 设计文档，把这个模块的规则、数据结构、流程、约束和关键逻辑写清楚。
开发的时候，我不是直接让 AI 看代码自己猜，而是先让 AI 理解这份文档，再根据文档实现代码。
后面即使换一个开发人员接手，他不需要重新阅读大量代码去理解这个复杂模块，而是可以先看这份文档快速建立 Context，再让 AI 根据文档和代码继续开发。
所以我现在比较强调的不是单纯让 AI 写代码，而是让 **代码、文档和 AI 形成一个持续同步的闭环**。
**文档定义意图，代码负责实现，AI 负责在两者之间保持同步。**

## 5. 产品文档：把 PRD 转换成可交互的 HTML，并实现 PRD 和 HTML 的双向同步

以前产品经理写 PRD，需求评审的时候基本就是产品经理照着文档讲，其他人听。
这种方式有一个很明显的问题，就是很多细节只能靠文字描述和口头解释，大家对需求的理解也容易产生偏差，很多问题要等到开发完成以后才发现。
所以我做了一套产品文档的 AI 化方案。
产品经理先提供 PRD，然后让 AI 根据 PRD 生成对应的可交互 HTML，把页面、交互流程、状态变化等内容直接表现出来。
这样需求评审的时候，不需要大家坐在那里听产品经理念大量文字，而是直接打开 HTML，按照真实的交互流程去体验。
比如一个按钮点下去会发生什么、不同状态下页面是什么样、整个业务流程怎么走，都可以直接看到。
这样就把原来“读 PRD、听 PRD”，变成了“看产品、操作产品”。
另外，我没有把 HTML 当成一次性的原型，而是建立了 **PRD ↔ HTML 的双向同步机制**。
PRD 发生变化时，让 AI 根据 PRD 更新 HTML；HTML 在实现过程中发生调整时，再让 AI 反向检查并同步 PRD。
所以最终形成的是：
**PRD → AI → 交互式 HTML → 需求评审**
以及：
**PRD ↔ AI ↔ HTML**
这样做的核心价值不是生成一个网页，而是把产品需求从静态文字变成了可以直接体验的交互式文档，降低产品、开发、测试之间的理解成本，同时尽可能在开发之前就发现需求问题，减少后期返工和出错。
我比较认可的一句话是：
**以前是大家听产品经理描述产品，现在是大家直接体验产品。**
